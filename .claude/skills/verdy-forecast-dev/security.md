# セキュリティの実装ルール（OWASP Top 10:2025）

このアプリで起こりうるリスクと、実装で守ることをまとめる。確認の手順は `docs/evaluation-procedure.md` にある。

## A01 アクセス制御の不備（SSRFを含む）

起こりうること: 他人がAPIを呼べてしまう。試合後に予想を書き換えられる。外部呼び出しの仕組みを悪用されて、内部のリソースにアクセスされる。

- APIは、何も指定しなければ認証が必須になる設定にする（`FallbackPolicy` に `RequireAuthenticatedUser`）。匿名にするのは、ヘルスチェックとログインの開始だけ。
- Entra ID のアプリは「シングルテナント」にして、エンタープライズアプリケーションで「割り当てが必要」をオンにする。割り当てるのは自分専用のユーザー1人だけ。
- 未ログインで API を呼んだときは、ログイン画面へリダイレクトせずに 401 を返す。リダイレクトは画面のパスだけで行う。
- 試合前の予想は、キックオフ時刻以降の変更と削除を拒否する（409）。判定はサーバー側で、`TimeProvider` の時刻を使う。
- CORS は設定しない（同じオリジンからだけ使う）。
- 外部へのHTTP呼び出しは、設定に書いたベースURL（許可リスト）だけ。URL やホスト名を、ユーザーの入力や取得データから組み立てない。許可リスト以外のホストが設定されていたら、起動時にエラーにする。

## A02 セキュリティ設定のミス

起こりうること: 開発用の機能や詳しいエラーが本番に出る。ブラウザを守るヘッダーがない。

- 本番では、開発者向けの例外ページ、OpenAPI の画面、詳しいエラーメッセージを出さない。
- すべての応答に次のヘッダーを付ける。

| ヘッダー | 値 |
|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self' https://login.microsoftonline.com; frame-ancestors 'none'` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Strict-Transport-Security` | 本番だけ。`max-age=31536000` |

- CSP では `'unsafe-inline'` と `'unsafe-eval'` を使わない。CSS はファイルとして読み込む。
- テスト用の偽ログインは `Testing` 環境だけで使う。それ以外の環境で有効になっていたら、起動時に例外を出して止める。この止まる仕組み自体もテストする。
- App Service は、HTTPSのみ、TLS 1.2以上、FTPは無効、基本認証での発行（SCM・FTP）は無効、リモートデバッグは無効にする。
- ストレージは、Blob の匿名アクセスを無効、共有キーでのアクセスを無効、TLS 1.2以上にする。
- SQL は Entra ID 認証だけにする（SQL 認証のパスワードは使わない）。

## A03 ソフトウェアのサプライチェーンの不備

起こりうること: 脆弱性のある部品や、ライセンスが変わった部品を使ってしまう。ビルドやデプロイの仕組みを乗っ取られる。

- NuGet はセントラルパッケージ管理（`Directory.Packages.props`）とロックファイルを使う。CI では `dotnet restore --locked-mode` を使う。
- npm は `package-lock.json` をコミットして、CI では `npm ci` を使う。
- 脆弱性のチェック: NuGetAudit（`dotnet restore` に組み込み。推移的な依存も対象）、`npm audit`、Dependabot、CodeQL。
- 部品の一覧表（SBOM）を CycloneDX で作って、ビルドの成果物として残す。
- 新しい部品を入れる前にライセンスを確認する。商用ライセンスや、条件がはっきりしないものは入れない。
- Azure DevOps では、フォーク（他人がコピーしたリポジトリ）からのPRはビルドしない（組織・プロジェクトの設定で「Disable building pull requests from forked repositories」）。シークレットを渡すことも、確認していないコードをビルドすることもなくなる。
- パイプラインのタスクとツールのバージョンを固定する。

## A04 暗号化の不備

起こりうること: 通信や保存データが読まれる。秘密情報が漏れる。

- 通信はすべて HTTPS。Cookie には `Secure` を付ける。
- APIキーは Key Vault に置いて、アプリの設定からは Key Vault 参照で読む。ローカルでは `dotnet user-secrets` を使う。
- SQL の保存時の暗号化（TDE）と、ストレージの保存時の暗号化は、既定のまま有効にしておく。
- ASP.NET Core の Data Protection のキー（Cookie の暗号化に使う）は、App Service の既定の保存場所を使う。Container Apps に移るときは、Blob に保存して Key Vault のキーで保護する。
- 独自の暗号処理を書かない。

## A05 インジェクション（XSSを含む）

起こりうること: SQL インジェクション。メモに入れた文字列がスクリプトとして動く。

- DB へのアクセスは EF Core の LINQ で行う。`FromSqlRaw` に文字列連結を使わない（どうしても SQL を書くときは `FromSql` の補間でパラメータ化する）。
- React で `dangerouslySetInnerHTML` を使わない。メモはテキストとして表示する。
- 入力は、APIの入口とアプリケーション層の両方で検証する。採点は決めた範囲と刻み、メモは最大文字数（要決定）、タグはマスタにあるものだけ、スコアは0以上の整数（上限あり）。
- AI（Azure AI Language）が返したタグ候補は、信用しない入力として扱う。マスタにあるタグだけを候補として採用する。

## A06 安全でない設計

起こりうること: 設計の段階で考えておくべきリスクが漏れる。

- `docs/threat-model.md` に脅威モデルを書く。守るものは、自分の記録、ログイン、Azureの費用。STRIDE の観点で洗い出して、対策とテストを1対1で対応させる。
- 悪用のケースをテストにする。たとえば、後出しで予想を書き換える、未来のデータを予測に混ぜる、大量にリクエストする、外部APIの無料枠を使い切らせる、など。
- POST などの書き込み系のエンドポイントには、レート制限（ASP.NET Core 標準の Rate Limiting）を付ける。
- API-Football の呼び出し回数を数えて、1日100回に近づいたら止める。

## A07 認証の不備

起こりうること: セッションを盗まれる。ログアウトしてもセッションが残る。

- ログインは Entra ID（OpenID Connect、認可コードフロー）を使う。パスワードを自分で保存しない。MFA は Entra 側で必須にする。
- クライアントの認証には、シークレットを使わない。マネージドIDをフェデレーション資格情報として使う（Microsoft.Identity.Web の `SignedAssertionFromManagedIdentity`）。ローカル開発は、本番とは別のアプリ登録を使う。
- セッションの Cookie の設定:
  - 名前を `__Host-` で始める。`Path=/` にして、`Domain` は付けない。
  - `Secure` と `HttpOnly` を付ける。
  - `SameSite` は `Strict` を第一候補にする。ただし Entra ID からリダイレクトされた直後に Cookie が送られず、ログインがループすることがある。そうなったら `Lax` にして、CSRF 対策はカスタムヘッダーで守る（要決定。Phase 5 で実際に試して決める）。
  - 有効期限は要決定（目安は8時間のスライディング）。
- ログアウトしたら、アプリの Cookie を消して、Entra ID からもサインアウトする。ログアウト後に API を呼ぶと 401 になることを確認する。
- ブラウザの JavaScript から読める場所（localStorage、sessionStorage、JavaScript から読める Cookie）に、トークンを置かない。

### CSRF 対策

- 画面からの API 呼び出しには、すべてカスタムヘッダー `X-CSRF: 1` を付ける。サーバーは、このヘッダーがない `/api` へのリクエストを拒否する。
- CORS を設定していないので、ほかのサイトからこのヘッダーを付けて送ろうとしても、ブラウザの事前確認（プリフライト）で止まる。
- この方式は、RFC 10017（ブラウザで動くアプリの OAuth のベストプラクティス）で推奨されている。

## A08 ソフトウェアやデータの完全性の不備

起こりうること: 予想や取り込んだデータが書き換えられる。壊れたデータを取り込む。デプロイの仕組みを悪用される。

- 予想のロックに加えて、予想・採点・レビューの変更は監査ログ（いつ、何が変わったか）に残す。メモの本文は監査ログに入れない。
- 取得したデータは、原本を Blob に保存して SHA-256 を記録する。取り込む前に、形式（必須項目、型、範囲）を検証する。おかしいデータは取り込まずに、ログに記録する。
- JSON の読み込みは `System.Text.Json` で、決まった型にだけ変換する。型を外部のデータから決める読み込み方はしない。
- main ブランチへの直接の push は禁止して、PR を必須にする。本番へのデプロイは、Azure DevOps の Environments で承認してから行う。
- Azure へのデプロイは、ワークロード ID フェデレーションのサービス接続で行う。パイプラインに Azure のシークレットを置かない。

## A09 セキュリティのログとアラートの不備

起こりうること: 攻撃や障害に気づけない。ログから個人のデータが漏れる。

- ログに残すもの: ログインの成功と失敗、401 と 403、CSRF 用ヘッダーがないリクエスト、ロック後の予想の変更の試み、レート制限、外部 API の失敗、ポイズンキュー。
- ログに残さないもの: メモの本文、Cookie、`Authorization` ヘッダー、トークン、APIキー。
- ログは構造化ログにして、相関 ID を付ける。
- Application Insights でアラートを作る。対象は、例外の急増、401 と 403 の急増、ポイズンキューへの移動、外部 API の連続した失敗。通知はメールで受け取る。
- Log Analytics には、1日あたりの取り込み上限を設定する（費用のため）。

## A10 例外的な状況の扱いミス

起こりうること: エラーのときに中途半端な状態が残る。エラーのときに守りが外れる（フェイルオープン）。

- 例外を握りつぶさない。想定した失敗は結果として扱い、想定外の失敗は上に投げて、共通の例外ハンドラーで ProblemDetails にする。
- 認可の判定でエラーが起きたら、拒否する（フェイルクローズ）。
- 外部 API にはタイムアウトとリトライを設定する。止まっているときは、前回のデータで表示して「データが古い」と知らせる。
- SQL の無料枠を使い切って DB が止まったときは、503 と分かりやすいメッセージを返す。スタックトレースは出さない。
- キューの処理は冪等にする。途中で失敗しても、トランザクションで中途半端な状態を残さない。
- 無料枠の上限（App Service の CPU、SQL、AI Language、API-Football）に達したときの動きを、仕様として決めておく。
