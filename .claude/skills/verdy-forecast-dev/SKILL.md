# verdy-forecast 開発ルール

## このプロジェクトについて

- 東京ヴェルディの次の試合について、勝ち・引き分け・負けの確率と予想スコアを出して、画面で見られるようにする。
- 試合後は、自分の採点・戦術タグ・メモ・試合前の予想を記録して、学習データにする。
- 使うのは開発者本人の1人だけ。インターネットに公開はするが、ログインした本人以外は何もできない。
- 費用はできるだけ0円、上限は月1,000円。
- 決定事項の全体は `docs/work-instructions.md`（作業指示書）、確認の方法は `docs/evaluation-procedure.md`（評価手順書）にある。

## 進め方（必ず守る）

1. 一度に1ステップだけ進める。作業指示書のステップ番号（例: 2-3）の単位で動く。
2. コードを書く前に、変更の方針を5行以内の箇条書きで示して、ユーザーの了承を待つ。1ファイル数行の小さな修正は除く。
3. 作業指示書で「要決定」になっていることに当たったら、推測で埋めない。選択肢と推奨を示して質問する。
4. 変更したら、関係するテストを追加・更新して、全テストを通してから完了を報告する。
5. git の commit と push は、ユーザーが指示したときだけ行う（どちらも実行前に確認が出る設定にしてある）。
6. 作業指示書で担当が「自分」になっているステップは、ユーザーが行う。Claude Code は、手順の案内とチェックリスト作りだけをする。
7. 報告は「何を変えたか」「テストの結果」「残っていること」を短く書く。

## 絶対に守るルール

### 予算

- 有料になるリソースを作らない、提案もしない。作る前に [azure-cost.md](azure-cost.md) の許可リストと照らし合わせる。
- 許可リストにないものは、費用を調べてユーザーに確認してから進める。

### データの取得元

- 自動で取得してよいのは、API-Football（無料プラン、1日100リクエスト以内）と Wikipedia（CC BY-SA、出典を画面に表示する）だけ。Wikipedia を使うときは、Wikimedia の User-Agent のルールに従い、連絡先として GitHub のリポジトリの URL を入れる。
- Jリーグ公式サイト、FBref、X（旧Twitter）からは自動で取得しない。規約で禁止または制限されているため。ヴェルディの詳細なスタッツは、ユーザーが公式サイトを見て手で入力する。
- 外部へのHTTP呼び出し先は、設定で決めたホストだけにする（許可リスト方式）。URLをユーザーの入力や外部データから組み立てない（SSRF対策）。
- このリポジトリは公開リポジトリ。取得したデータ、自分の採点やメモ、分析の出力結果をコミットしない。

### 秘密情報

- APIキー、接続文字列、パスワードを、コード・設定ファイル・ログ・テストデータに書かない。
- ローカルでは `dotnet user-secrets`、Azureでは Key Vault を使う。値を入れるのはユーザー自身。Claude Code は秘密情報の値をユーザーに聞かないし、保存場所も読まない。
- Azureのサービスには、できる限りパスワードを使わずにマネージドIDで接続する。

### Azure の操作

- Claude Code は Azure を操作しない。`az`、`azd`、`Connect-AzAccount`、`func azure` を実行しない（`.claude/settings.json` でも禁止している）。
- Azure を変更するのは、ユーザーのポータル操作か Azure CLI、または承認されたパイプラインだけ。Azure での作業が必要になったら、ポータルでの操作手順か、ユーザーが実行するコマンドを書いて渡し、そこで止まる。
- `~/.azure`（Azure CLI のログイン情報）と、`dotnet user-secrets` の保存場所を読まない。
- ローカルの開発とテストでは、Azure のサービスに接続しない。SQL と Storage は Docker（SQL Server、Azurite）を使い、AI Language は偽物の実装に差し替える。

### 学習データ

- 試合前の予想は、キックオフ時刻を過ぎたら変更も削除もできない。サーバー側で拒否する。
- 試合後の採点・タグ・メモは、その試合より後の試合の予測にだけ使う。予測に使う材料は、必ず「キックオフ時点で分かっていたデータ」だけで作る（データリーケージの防止）。
- 画面では、自分の予想を入力するまで、モデルの予想を見せない。

### 認証（BFF方式）

- ブラウザにはアクセストークンもIDトークンも渡さない。ブラウザが持つのはセッションのCookieだけ。
- APIは、何も指定しなければ認証が必須になる設定にする（フォールバックポリシー）。匿名で呼べるのは、ヘルスチェックとログインの開始だけ。
- テスト用の偽ログインは `Testing` 環境だけで使う。本番で有効になっていたら、起動時に例外を出して止める。

## 変更の種類ごとのチェックリスト

### ドメインのルールや計算を変えるとき

- [ ] 変更は `VerdyForecast.Domain` の中だけで閉じている（外部ライブラリやI/Oを持ち込まない）
- [ ] 境界値のテストがある（キックオフちょうど、同点、0-0、データ0件など）
- [ ] 現在時刻は `TimeProvider` から取っている（`DateTime.Now` や `DateTime.UtcNow` を直接使わない）

### APIのエンドポイントを足す・変えるとき

- [ ] 認可は既定（認証必須）のまま
- [ ] 状態を変えるリクエスト（POST・PUT・PATCH・DELETE）は、CSRF対策のカスタムヘッダーがないと拒否される
- [ ] 入力を検証している（型、範囲、長さ）
- [ ] エラーは ProblemDetails で返し、例外の詳細やスタックトレースを返さない
- [ ] WebApplicationFactory の統合テストがある（未認証で401、ヘッダーなしで拒否、正常系）

### 外部データの取得を足す・変えるとき

- [ ] 呼び出し先は許可リストのホストだけ
- [ ] タイムアウトとリトライがある（`Microsoft.Extensions.Http.Resilience`）
- [ ] 受け取ったデータは、まず原本をBlobに保存して SHA-256 も記録する。そのあと形式を検証してから取り込む
- [ ] 同じデータを2回取り込んでも結果が変わらない（冪等）
- [ ] 外部APIが止まっていても画面は前回のデータで動き、「データが古い」と表示される

### 画面を足す・変えるとき

- [ ] `dangerouslySetInnerHTML` を使わない。メモなどの文字列はテキストとして表示する
- [ ] トークンや個人のデータを localStorage・sessionStorage に入れない
- [ ] インラインの script と style を使わない（CSPを緩めない）
- [ ] API呼び出しは共通の fetch ラッパーを通す（CSRF用ヘッダーを付ける、401ならログインへ移動する）
- [ ] Vitest のテストがある。画面の流れが変わるなら Playwright のテストも足す

### 試合後の処理（Azure Functions）を足す・変えるとき

- [ ] 1つのメッセージで1つの処理をする。メッセージにはIDと種類だけを入れる（個人のデータを入れない）
- [ ] 同じメッセージが2回届いても、二重に処理しない
- [ ] 失敗したら例外を握りつぶさない。リトライして、それでもだめならポイズンキューに送ってアラートを出す
- [ ] 接続はマネージドIDで行う（接続文字列を使わない）

### Azureのリソースを足す・変えるとき

- [ ] Bicep で書く（ポータルでの手作業はしない。確認のために見るのはよい）
- [ ] [azure-cost.md](azure-cost.md) の許可リストに入っている
- [ ] PSRule for Azure のチェックを通る
- [ ] 適用はパイプラインで行う。what-if の結果はユーザーが確認して承認する（Claude Code は Azure に対して実行しない）

### パッケージを足すとき

- [ ] ライセンスを確認した（商用ライセンスや不明なものは入れない。例: FluentAssertions v8 は使わない）
- [ ] 既知の脆弱性がない（`dotnet list package --vulnerable --include-transitive`、`npm audit`）
- [ ] バージョンを固定して、ロックファイル（`packages.lock.json`、`package-lock.json`）を更新した
- [ ] 本当に必要か考えた（標準ライブラリで済むなら入れない）

## 完了の定義

- ビルドで警告が0件（警告はエラーとして扱う）
- 全テストが成功（.NET と Vitest。関係する場合は Playwright も）
- 依存ルールのテスト（ArchUnitNET）が成功
- 差分に秘密情報、取得したデータ、自分の記録が入っていない
- 作業指示書の該当ステップの完了条件を満たしている
