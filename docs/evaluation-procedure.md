- 版: 0.2（下書き。担当の分け方を追加）
- 作成日: 2026-11-23
- 関連: 作業指示書 `docs/work-instructions.md`、開発用スキル `.claude/skills/verdy-forecast-dev/`

## 1. この文書について

- verdy-forecast が、機能・品質・セキュリティ・費用・予測の精度の面で、決めた基準を満たしているかを確かめる手順書。
- 合格基準の数字は、最初の目安。実際にやってみて、厳しすぎたり緩すぎたりしたら、理由を書いて見直す。
- 評価の結果は `docs/evaluation-records/` に記録する（11章のテンプレート）。

### 担当の分け方

| 担当 | やること |
|---|---|
| 自動（CI・GitHub） | PR やデプロイのたびに、パイプラインや GitHub が自動で行うチェック。結果は自分が見る |
| Claude Code | 自分の PC の中だけで動く検査（テスト、カバレッジ、ミューテーションテスト、ローカル環境への ZAP、予測モデルの検証の計算）と、記録の下書き |
| 自分 | Azure ポータルと Azure CLI での確認、Entra のサインインログ、ブラウザの開発者ツールでの確認、Burp Suite での手動の確認、費用の確認、最終的な合否の判断 |

- Azure CLI のコマンドは自分が実行する。Claude Code には実行させない（権限ルールでも禁止している）。使い終わったら `az logout` する。
- Claude Code が下書きした記録も、合否は自分が決める。

### 安全のための決まり

- 検査は、自分のアプリとリソースにだけ行う。
- 攻撃に近い強い検査（ZAP のアクティブスキャン、Burp Suite での手動の攻撃）は、自分の PC で動かしたアプリ（`Testing` 環境）にだけ行う。
- Azure 上の本番には、通信を見るだけの軽い検査（ZAP のベースラインスキャン）だけを行う。App Service F1 の CPU の上限もあるため。
- Azure 上の検査は、Microsoft のクラウド侵入テストのルール（Rules of Engagement）に従う。自分のリソースなら事前の申請はいらないが、DoS（サービス妨害）にあたるテストや、大量の通信を発生させる自動テストは禁止されている。

## 5. テストとアーキテクチャの評価

### 5.1 テストの品質（担当: Claude Code が実行、自分が結果を見る）

1. `dotnet test` と `npm run test` と `npx playwright test` が、全部成功することを確かめる。
2. カバレッジを取って、合格基準と比べる（`dotnet test --coverage --coverage-output-format cobertura`）。
3. Domain のミューテーションテストを実行して、スコアを記録する（`dotnet stryker --test-runner mtp`。MTP 用のランナーはプレビュー機能なので、うまく動かないときは理由を記録する）。
4. 生き残ったミューテーション（テストで見つけられなかったバグ）を見て、足りないテストを足す。

### 5.2 依存ルール（担当: 自動（CI））

- `tests/VerdyForecast.ArchitectureTests` が成功することを確かめる。
- わざと Domain から Infrastructure を参照するコードを入れて、テストが落ちることを、Phase 1 で一度確かめておく。

### 5.3 アーキテクチャの比べ方（担当: Claude Code が実装と数字の集計、自分が振り返り）

同じ条件で次の変更課題をこなして、かかった手間を記録して比べる。課題は v1 の完成後に、1つずつ別の PR で行う。

| No | 変更課題 | 主に試されるところ |
|---|---|---|
| T1 | 試合結果の取得元を、API-Football から CSV の取り込みに差し替える | クリーンアーキテクチャ（差し替えやすさ） |
| T2 | 評価指標に対数損失（log loss）を足す | クリーンアーキテクチャ（ドメインの変更の閉じ方） |
| T3 | 試合後の処理に「戦術タグの下書きを作る」ステップを足す | イベント駆動（処理の足しやすさ） |
| T4 | 同じメッセージを重複して送り、さらに途中の処理をわざと失敗させる | イベント駆動（二重処理の防止と、やり直し） |

記録すること:

| 項目 | 内容 |
|---|---|
| 変更したファイルの数と行数 | git の差分から |
| 触った層の数 | Domain、Application、Infrastructure、Api、Functions のうちいくつか |
| 足したテストの数 | |
| かかった時間 | だいたいでよい |
| 迷ったところ | 自由に書く |
| 難しさ | 5段階 |

最後に自分で、「クリーンアーキテクチャがよかったところ・面倒だったところ」「イベント駆動がよかったところ・面倒だったところ」を、それぞれ3行で振り返る。

| API-Football | アプリのデータの状況の画面（S7） | 1日100回の範囲内 |

予算アラートは、しきい値を超えてから届くまでに時間がかかることがある。アラートが届く前に、日ごとの費用で気づけるようにしておく。

## 9. 予測モデルの評価

担当: Claude Code が自分の PC の `analysis/` で計算して、記録の下書きを作る。データは自分の PC の中だけで扱い、リポジトリには入れない。結果の判断と振り返りは自分。

### 9.1 評価指標

勝ち・引き分け・負けの3つの結果には順番がある（勝ち＞引き分け＞負け）ので、主な指標には RPS（Ranked Probability Score）を使う。どれも小さいほど良い。

- ヴェルディの試合（自分の予想との比較）は、ヴェルディから見た順（勝ち、引き分け、負け）で計算する。
- J1 の全試合でのモデルの検証は、ホームから見た順（ホーム勝ち、引き分け、アウェイ勝ち）で計算する。

| 指標 | 計算 | 範囲 |
|---|---|---|
| RPS（主な指標） | 予想の確率を p₁, p₂, p₃、結果を o₁, o₂, o₃（起きた結果だけ1、ほかは0）として、RPS = ½ × {(p₁ − o₁)² + (p₁ + p₂ − o₁ − o₂)²} | 0〜1 |
| Brier スコア | (p₁ − o₁)² + (p₂ − o₂)² + (p₃ − o₃)² | 0〜2 |
| 対数損失 | −ln（起きた結果に付けていた確率） | 0〜∞ |
| 的中 | 一番高い確率を付けた結果が起きたら1 | 0 か 1 |

計算の例: 予想が「勝ち50%・分け30%・負け20%」で、結果が引き分けのとき。

- RPS = ½ × {(0.5 − 0)² + (0.8 − 1)²} = ½ × (0.25 + 0.04) = 0.145
- Brier スコア = 0.25 + 0.49 + 0.04 = 0.78
- 対数損失 = −ln(0.3) ≈ 1.204

予想スコアは、スコアの完全一致と、得失点差の一致の割合も記録する。

### 9.2 比べる相手（ベースライン）

| ベースライン | 中身 |
|---|---|
| 一様 | いつも勝ち・分け・負けを 1/3 ずつにする |
| リーグ平均の頻度 | 過去のシーズンのホーム勝ち・引き分け・アウェイ勝ちの割合を、いつもそのまま使う |
| 自分の予想 | 試合前に入れた自分の予想。％がないときは、作業指示書の D8 のルール（選んだ結果に60%、残りは隣の結果に多く配る）で確率に直す。評価には、ロックの時点で保存した確率を使う |

モデルが2つのベースライン（一様、リーグ平均の頻度）に勝てないときは、画面のモデルの予想に「参考値」と書いて、モデルを見直す。

### 9.3 検証のやり方（ウォークフォワード）

1. 過去のシーズンの J1 の全試合を、キックオフ日時の順に並べる。
2. 試合ごとに、その試合のキックオフより前のデータだけでモデルを更新して、予想を作る。
3. その試合の結果で評価指標を計算して、記録する。
4. 次の試合に進んで、2〜3 を繰り返す。
5. シーズンごとと全体で、平均を出してベースラインと比べる。

- データをシャッフルした交差検証はしない（未来のデータで過去を予想してしまうため）。
- モデルの評価は、ヴェルディの試合だけでなく J1 の全試合で行う（試合数を増やすため）。自分の予想との比較は、ヴェルディの試合だけで行う。

### 9.4 データリーケージのチェック

- 自動テスト（スキルの testing.md の「データリーケージのテスト」）が成功している。
- 本番の DB で、保存したモデルの予想すべての「材料に使ったデータの時点」がキックオフより前になっていることを確かめる（Claude Code が SQL を用意して、自分がポータルのクエリエディターで実行する）。
- 自分の予想すべてについて、入力日時がキックオフより前になっていることを、同じ方法で確かめる。

### 9.5 確率の当たり具合（キャリブレーション）

- 予想の確率を10%刻みのグループに分けて、グループごとに「予想した確率の平均」と「実際に起きた割合」を比べる。
- 両方が近いほど良い。試合数が少ないうちは、ばらつきが大きいので参考程度にする。

### 9.6 シーズンが終わったときの振り返り

| 項目 | 内容 |
|---|---|
| モデルの平均 RPS | ヴェルディの試合と、J1 の全試合 |
| 自分の平均 RPS | ヴェルディの試合 |
| ベースラインの平均 RPS | 一様、リーグ平均の頻度 |
| 的中数 | モデルと自分 |
| モデルが大きく外した試合 | 上位3試合と、外れた理由の考察 |
| 自分が大きく外した試合 | 上位3試合と、外れた理由の考察 |
| 次のシーズンに変えること | v2・v3 の計画に反映する |

## 10. 障害が起きたときの振る舞い

| 状況 | 担当 | 起こし方 | 期待する結果 |
|---|---|---|---|
| API-Football に届かない | 自動テスト | 呼び出し先を届かないアドレスにする | 前回のデータで表示、「データが古い」と表示、ログに記録 |
| API-Football の1日の上限に近い | 自動テスト | 呼び出し回数のカウントを上限近くにする | それ以上呼ばずに止まる |
| SQL が止まっている | 自動テスト | DB のコンテナを止める | 503 と分かりやすいメッセージ |
| AI Language が使えない | 自動テスト | 呼び出し先を届かないアドレスにする | タグの候補なしで、手で選べる |
| キューの処理が何度も失敗する | 自動テスト、アラートは自分 | わざと例外を起こす | リトライのあとポイズンキューへ移る。DB に中途半端な状態が残らない。本番ではアラートが届く |
| 同じメッセージが2回届く | 自動テスト | 同じメッセージを2回送る | 処理は1回分だけ |
| App Service F1 の CPU の上限 | 自分 | （本番でたまたま起きたとき） | その日は止まる。翌日には戻る。起きた日を記録する |
